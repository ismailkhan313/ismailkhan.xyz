The premise of the *AI-native SDLC* is a single observation about where time
goes: organizations adopted agentic coding and got a much faster build phase,
but left every process around the build phase untouched.[^sdlc-playbook] The
approval gates, reviews, handoffs, and policies were sized for an era when
writing code was the expensive part. Once it isn't, they become the
constraint.

Anthropic's Applied AI team wrote this playbook from customer engagements, and
it is best read as what it is: a vendor's account of how to restructure a
lifecycle around that vendor's tools. Its value is that it is specific — twelve
concrete plays, each with prerequisites, a governance story, and the metric
that says whether it worked — rather than an argument that AI is
transformative.

## The bottleneck moved

The traditional SDLC runs six stages — plan, design, build, test, deploy,
maintain — each owned by a different role, with work moving between them
through documents, tickets, and sign-offs. That structure exists to produce
accountability during what used to be weeks or quarters of implementation.

When implementation collapses to agent speed, three things follow:[^sdlc-playbook]

1. **The bottleneck moves outward**, to plan, review/test, and deploy, which
   still run at human speed.
2. **The controls stop matching reality.** Reading every line made sense when a
   person wrote every line; it doesn't survive agents writing most of the diff.
3. **Governance costs rise**, because exceptions still route through committees
   that meet weekly or monthly.

The security review is the sharpest case. A security team sized for human
output faces a queue that either grows without bound or gets waved through. A
regulated organization can accept neither, so the checks themselves have to run
at agent speed.

## Line to loop

The playbook's structural claim is that the lifecycle stops being a line and
becomes a loop with AI embedded at each point, and with handover between stages
automated rather than manual. Production is not the end of the process; a
breached control band in production writes the next `intent.md` and the loop
runs again.

| Stage | Traditional | AI-native |
| --- | --- | --- |
| Plan | Requirements gathered by committee, distilled through workshops and sign-offs | Claude synthesizes pain points from the sources into `intent.md` — human readable, machine actionable |
| Design | Spec written by analysts, parsed by designers | Requirements and design compressed into one working session, guided by standards encoded as skills |
| Build | Tests and code handwritten, documentation after the fact | Tests and code generated by AI; institutional knowledge maintained as versioned `CLAUDE.md` files and skills |
| Test | QA gates at stage boundaries | Continuous evals woven through implementation |
| Deploy | Humans review every line; governance happens in review cycles | Layers of agentic review, human review reserved for regulated and critical code; governance enforced as the AI acts |
| Maintain | Humans watch production for bugs | Agents monitor deployments; a breached control band becomes a new `intent.md` |

## The committed artifact is the spine

What holds the AI-native column together is not the model — it is that every
stage ends by writing a file to version control and the next stage begins by
reading it. The chain runs `intent.md` → `spec.md` → `plan.md` → the diff and
its tests → the PR and its review findings → the incident record → the next
`intent.md`.

Two properties make this work. Markdown is the medium for the early stages
because a product owner and an agent can both read and act on the same file;
from build onward the artifact is code and its records. And the chain of
commits *is* the audit trail — who asked for what, what the agent produced, who
approved it — which is what lets the playbook argue that the old control
objectives survive under new enforcement rather than being abandoned.

This is the same instinct as [context engineering](/context-engineering.md)
applied to a process rather than a session: the file on disk, not the
conversation, is what carries state across a boundary.

## The plays

Twelve plays, grouped into six stages, each covering what changes, how to start,
concrete steps, governance considerations, and how to measure it. They are
modular and carry explicit prerequisites, so an organization can transform one
stage without transforming the others.

**Stage 1: Plan** — [Capture as intent.md](</AI-Native SDLC/capture-intent.md>)

**Stage 2: Design** — [Requirements and design](</AI-Native SDLC/requirements-and-design.md>)

**Stage 3: Build** — [Plan mode as the default](</AI-Native SDLC/plan-mode.md>) ·
[The CLAUDE.md](</AI-Native SDLC/claude-md.md>) ·
[Skills as institutional knowledge](</AI-Native SDLC/skills-as-institutional-knowledge.md>) ·
[Parallel sessions and subagents](</AI-Native SDLC/parallel-sessions-and-subagents.md>)

**Stage 4: Test** — [Give Claude a feedback loop](</AI-Native SDLC/feedback-loop.md>) ·
[Continuous evals in CI](</AI-Native SDLC/continuous-evals.md>)

**Stage 5: Deploy** — [AI in the PR review loop](</AI-Native SDLC/ai-pr-review.md>) ·
[Hooks as approval gates](</AI-Native SDLC/hooks-as-approval-gates.md>) ·
[CI/CD integration and deployment](</AI-Native SDLC/ci-cd-integration.md>)

**Stage 6: Maintain** — [Closing the loop on metrics](</AI-Native SDLC/closing-the-loop.md>)

Six plays have no prerequisites at all — capture intent, `CLAUDE.md`, skills,
the feedback loop, hooks, and plan mode — which is where the playbook says to
start. The dependencies then stack: subagents and evals want `CLAUDE.md`,
requirements-and-design wants captured intent and skills, PR review wants evals
and subagents, CI/CD wants PR review and hooks, and closing the loop wants CI/CD
and captured intent.

## Advisory controls and deterministic ones

The distinction the playbook is most careful about, and the one most worth
carrying away, is between two kinds of control:

- **A skill is advisory.** It makes Claude *likely* to apply a policy while the
  code is written. Nothing forces a session to comply.
- **A hook is deterministic.** It runs before the action and can allow, ask, or
  block, every time, for everyone.

A policy that must always hold needs both: the skill makes violations rare, the
hook makes them close to impossible. This is why
[Agent Skills](/agent-skills.md) show up in this playbook as a *governance*
mechanism rather than a productivity one, and why the
[hooks play](</AI-Native SDLC/hooks-as-approval-gates.md>) is where the
regulated-enterprise configuration lives.

The same layering appears at the top: humans remain accountable for every
decision requiring judgment, but their attention concentrates at gates —
reviewing what the agent flagged — rather than starting each stage from scratch.
That is the [human-in-the-loop pattern](</Agentic Design Patterns/human-in-the-loop.md>)
applied at process scale.

## Measurement

Every play names a leading and a lagging indicator, and nearly all of them are
read from systems that already exist: Git timestamps, PR metadata, CI check
runs, the OpenTelemetry export, the incident tracker. That is deliberate and
worth noting as a limitation — these are proxy metrics available without new
instrumentation, not evidence that the process change caused the outcome. The
lagging indicators (rework rate, change failure rate, defects escaping to
production, DORA measures) are the honest ones; the leading indicators mostly
measure cycle time.
